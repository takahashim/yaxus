# Engine の非同期化と、Web を含めた全体の設計

状態: 設計 (2026-11-14 に全体を見直し、レビューを受けて改訂)。後方互換性は考えない。
下の「出発点」の部分は main に入っている。この文書が提案するのは、その上の設計である。

## 要約

WebGPU は GPU の完了をブロックして待てない。これを理由に、Web は Engine を使わず、
段落の分割、履歴、出力の組み立て、統計を、runtime とは別に自前で持っている。
問題は Engine ではなく、**同期か非同期かで層が割れていること**で、Engine より上の層
(`Generator`、`Session`、文書、server の worker) がすべて同期を前提にしている。

方針は 1 つ。**推論から出力までのスケジューラを 1 つにし、それを非同期で書く。**
同期の環境 (server、CLI) はそれを `block_on` で動かし、Web は `spawn_local` で動かす。
Web 固有のコードは、GGUF の読み込みと JS との接続だけにする。

## 出発点 (実施済み、main に入っている)

- `AsyncReadback` と `Engine::step_async`。`Engine::step` は `SyncReadback` の型に限り、1 回 poll する。
- Web の `Translator` は Engine で翻訳し、prefix 再利用が効いている
  (12 段落の文書の prefill 2212 ms → 約 390 ms、出力は再利用なしとバイト単位で同じ)。
- ネイティブの速度と出力は変わらない (2B、19 文: 下書きあり 61.8 tok/s、なし 26.65 tok/s、19/19 一致)。

これは設計の土台として正しかった。ただ、Web の `Translator` はまだ 1 リクエストずつ、
段落を自前で処理している。ここから先を、層ごとに作り直す。

## いまの構造と、割れている所

```
Backend ─ Model ─ Engine ─ Generator (dyn、同期、Send) ─ Session<T> ─┬─ DocRun / run_document (CLI)
                                                                     ├─ server の worker (Docs、jobs)
                                                                     └─ run_request
yaxus-web: Translator が Model→Engine を直接使い、分割・履歴・出力・統計を自前で持つ (約 300 行の重複)
```

- Web の `translate_inner`、`fit_segment`、`decode_segment`、`Output`、`Stats` は、runtime の
  `DocJob`、`Session`、`DocRun` の働きを別の形で書き直したもの。
- 長い段落を文に分ける処理 (`split_for_context`、トークン数で見る) は Web にしかない。
  native は段落の分割しか持たず、長い段落は 1 つのまま訳す。
- 同時に走れるのは、server の worker だけ (`Docs` で複数の文書をつなぐ)。Web は 1 件ずつ。

## 設計

### 1. Engine: 容量を見て受け付ける

`Engine::admit` は、`target.begin` が KV のページ不足で失敗すると `Event::Error` にしている。
同時に複数のリクエストを走らせる前提では、これは待たせるべき状況であって、エラーではない。

上限は 2 つあり、別々に判定する。

- **系列ごとの長さ** (`max_pos`): 1 つの系列が取れる位置の上限。`prompt + max_new > max_pos` の要求は、
  単独でも収まらないので、`Event::Error` にする (待っても改善しない)。
- **アリーナの物理ページ数** (全系列で共有): 単独で収まる要求は、空きが出るまで `waiting` に残す。
  ストリームが終わるたびに再判定する。

**予約の規則 (初回の実装)。** 各要求の最大ページ数をそのまま予約する。prefix の再利用分は差し引かない。

```
reserve(req) = ceil(min(prompt + max_new, max_pos) / PAGE)
```

- 一律の `+1` ページは足さない。投機の検証 (`verify`) が一時的に `len` の先まで書くが、提案数 `k` は
  残りの出力予算 `left = max_new - generated` 以下に制限されている (`engine/mod.rs` の `propose`:
  `hint_k.min(left)`、`draft_k.min(left)`)。検証後の一時的な KV 長は `prompt + generated + k` で、
  `prompt + max_new` を超えない。`+1` を足すと、4,096 トークンのアリーナ (32 ページ) に 4,096 トークンの
  要求が収まらなくなり、投機を使わない Web でも受け付けられなくなる。
  下書きモデルがあるときは、下書き側のアリーナにも同じ式で予約する。
- **その要求だけで** 予約がアリーナの総ページ数を超える場合は、待っても改善しないので、その場で
  `Event::Error` にする (`max_pos` を超える場合と同じ扱い)。永久に待つ要求を作らない。
- 単独では収まる要求は、受け付けた要求の予約の合計がアリーナの総ページ数を超えるあいだ、`waiting` に残す。
  終了済みで cache に残っている系列は、追い出せるので数えない。
- prefix 分を差し引かないのは、検証しやすさのため。再利用で共有されるページは、使用中として一度だけ
  数える必要があり、末尾の部分ページは `fork` がコピーするので、そのページも別に数える必要がある
  (`kv.rs` の `fork`)。この会計は、実際の再利用は既存の `KvCache` に任せたままで、受付の条件だけを
  単純にしておく。実測で詰まりが目立つなら、あとで差し引く式に替える。
- 最悪の出力長 (`max_new`) で予約すると無駄が大きい。同じく、実測で目立つなら、出力が予約を超えた
  ストリームを止めて再計算に回す (preemption) を足す。
- `max_streams` は上限として残すが、実際の同時数は KV の容量が決める。

`step_async` の戻り値の意味は、先の改訂のまま: `Err` はバックエンドの失敗で、エンジンは作り直すまで
使わない。要求ごとの失敗は `Event::Error`。

**キャンセル。** `Engine::cancel(id)` を足す。呼べるのはステップの合間だけ (ステップの Future が
`&mut self` を持っているので、型で保証される)。

- `waiting` にいる要求は、取り除いて `Done { Cancelled }` を出す。
- 実行中のストリームは、印を付け、現在のステップを完了させてから、`sweep` が `Done { Cancelled }` を出す。
- 今の `emit` が `false` を返す経路は、トークンが届いて初めて効くので、容量待ちの要求には効かない。
  `cancel` はそれを補う。両方を残す。

### 2. `Generator`: 非同期で、`Send` を要求しない

```rust
pub trait Generator {
    fn submit(&mut self, req: Request);
    fn step<'a>(&'a mut self, emit: &'a mut dyn FnMut(Event) -> bool) -> LocalBoxFuture<'a, Result<bool>>;
    // fresh_id、abort_all、score、... は今のまま (score も非同期にする)
}
```

- `LocalBoxFuture` (Send でない) にする。WebGPU の Future は Send でないので、`Generator: Send` は外す。
- ネイティブの推論スレッドへ渡す境界でだけ、`Box<dyn Generator + Send>` を要求する。
- ステップごとの boxing は、ステップが ms 単位なので無視できる。必要なら `enum AnyEngine { Cpu, Gpu }`
  にして dyn を避けることもできる (要測定、いまは dyn のまま)。
- `Engine::step` (同期) は、テストと CLI の小さな用途のために `block_on` の薄い包みとして残す。

### 3. `yaxus-runtime` を、ターゲットに依存しない非同期のコアにする

runtime を 2 つに分ける。

- **コア (wasm でも動く)**: `Prompt`、`Memory`、`Session<T>`、`DocJob` / `DocRun`、`Scheduler`。
  `tokio` もファイルも使わない。`futures` の型だけに頼る。
- **`native` フィーチャー**: モデルの解決 (`resolve.rs`、HF キャッシュ)、バックエンド (CPU、GPU) の読み込み (`load.rs`)。

`Session::step`、`DocRun` の実行ループは `async fn` にする。同期版は作らない (呼び出し側が `block_on` する)。

### 4. `Scheduler`: server の worker を一般化する

server の `worker::run` が、すでに正しい形をしている: 入口の queue から job を受け、Engine を回し、
文書のチェーンをつなぎ、イベントを返す。これを runtime のコアに移し、server と Web で共有する。

```rust
pub struct Scheduler { engine: Box<dyn Generator>, tok: Rc<Tokenizer>, memory: Memory, session, docs, ... }

impl Scheduler {
    /// jobs が尽きるまで回る。待つ物が無いときは jobs.next().await で眠る。
    pub async fn run(&mut self, jobs: impl JobSource) -> Result<(), Poisoned>;
}
pub enum Job {
    Single { prompt, max_new_tokens, events },
    Document { job: DocJob, events },
    Cancel { id },
}
```

- イベントの出口は、`yaxus-api` の `StreamEvent` / `DocumentEvent` をそのまま使う
  (`Delta { segment, text }`、`SegmentDone`、`Done { usage }`、`Error`)。server は SSE に、Web は JS の関数に流す。
- `JobSource` は `async fn next()` と `try_next()` を持つ小さなトレイト。server は `tokio::sync::mpsc`
  を包んだもの (今の `Jobs` と同じ上限と計数)、Web は `futures_channel::mpsc` を包んだもの。
- **server の推論スレッド**は、`pollster::block_on(scheduler.run(jobs))` を 1 回呼ぶだけになる。
  ネイティブの future はすべて即座に完了するので、待ち (`jobs.next().await`) 以外で眠らない。
- **キャンセル。** `Job::Cancel` は、新規ジョブの受付の上限 (`jobs.limit()`) に関係なく処理する。
  今の worker は、待機中の要求が上限に達すると job を取り込まないので、キャンセルが後ろに詰まる。
  `Cancel` は別の経路 (専用の小さな channel、または job より先に読む) で受け、`Engine::cancel` を呼ぶ。
  進行中のステップは捨てずに、完了してから対象を終える。
  **文書のキャンセル**は、その文書に属する待機中と実行中の両方のセグメントを取り消し、
  以後のセグメントは投入しない (`DocRun::stop` に `Engine::cancel` を足す)。
- **失敗の方針を 1 つにする。** 今は「panic ならエンジンを捨てて停止」と「`Err` なら全部を失敗にして続行」
  の 2 つがある。`step` の `Err` はバックエンドの失敗でありエンジンは使えないので、両者を
  `Poisoned` に統一する: 全リクエストを失敗にし、`run` は返る。server は 503 と `/healthz` で再起動を促し
  (今の panic の扱い)、Web は `broken` にして Worker を作り直す (今のまま)。
  どの時点で完了を通知するかは、次の節で決める。

### 4a. GPU 障害と完了通知 (WebGPU)

**最初の段階 (一文書を最後まで駆動する Translator) は、今のスコープのままでよい。** 今の Web は、
翻訳ごとに GPU のエラースコープを開き、翻訳の最後に `watch.finish().await` で遅れて届くエラーを
確かめてから成功にしている。1 つの文書の翻訳が Translator に属しているので、障害はその翻訳のものと
決められる。同じ文書のチェーンから複数のセグメントを同じパスで進めても、帰属先は 1 つの文書である。
文書内のバッチ (下の実施順 2) は、この現行の仕組みで足りる。

以下は、**独立した複数の翻訳を同じパスで進める段階** (常駐 `Scheduler`) の設計である。翻訳ごとに
スコープを開く方式では、障害をどの翻訳のものか決められない。WebGPU のエラースコープはデバイス単位の
スタックで、パスは複数の要求に共通だからである。

- **スコープの単位を、翻訳からステップに替える。** スコープは `Engine::step_async` の**冒頭**、受付
  (`admit`) より前で開き、そのステップのパスの終わりの待ちで閉じる。`begin_pass` では遅い:
  prefix 再利用の KV コピーは `Model::begin` (受付時) から発行され、`forward` の中でも `begin_pass` より
  前にページコピーが走るので、`begin_pass` で開くと、これらの GPU 作業がスコープから漏れる。
  境界は「受付時のコピーから、対象のコマンドの submit と読み戻しの完了まで」と定義する。
  ステップは 1 つずつ直列に await するので、スコープは入れ子にならない。
- **スコープの結果を step の成否に含める。** パスの終わりの待ち (argmax の読み戻し) は、
  読み戻しが終わったあとにスコープの結果を取り、エラーがあれば `Err` を返す。
  これにより、読み戻しの前に出したトークンも、後に出す `Done` も、エラーのないパスのものだけになる。
- **トークンと `Done` は、ステップが検証されてから出す。** `Engine` は argmax の結果を受け取ってから
  `emit` するので、この順序が自然に守られる。守るべき規則は 2 つ:
  1. `emit` は、そのステップの読み戻しとスコープの結果が `Ok` のあとにだけ呼ぶ。
     ただし受付で起きる `Done` (空のプロンプト、応答キャッシュ、容量不足のエラー) は、GPU を使わないので、
     検証を待たずに出してよい。KV コピーを発行したステップだけが、検証の対象になる。
  2. 読み戻しを持たないステップ (完了しない prompt のチャンク、コピーだけが走ったステップ) にも、
     スコープを閉じる待ちを置く。`AsyncReadback` に、argmax と別の `end_pass` (既定は何もしない) を足し、
     Engine が各ステップの終わりに必ず呼ぶ。チャンクごとに CPU と GPU の往復が 1 回増える。
     チャンクの計算に比べて小さいはずだが、未測定 (下の決めきれていない点)。
- **帰属は試みない。** エラーがあれば、そのステップに乗っていた要求のどれのせいかは分からないので、
  デバイス全体を信用しない (`Poisoned`)。全要求 (実行中と待機中) を `Error` にし、`Done` は出さない。
  デバイスロスト (`device.lost`) も同じ経路にする。
- **ネイティブ**は、スコープを持たず、`end_pass` も何もしない。

### 5. 文書の構築を共通にする

共通化には、挙動を変えない部分と、訳を変える部分がある。**別の段階にする。**

**挙動を変えない共通化 (段階 1)。** Web の `Translator` を共有の実行ループ (`run_document_async`) に載せる。
分割、履歴、チェーンの方針は、今のそれぞれのものをそのまま使う。

- Web: セグメントは今の `split_for_context` で作り (`Segment { text, paragraph }` を `DocJob` に渡せるようにする)、
  チェーンは 1 本、履歴は文字数 (`HISTORY_CHARS`) で、**出力の上限に達した訳は次の履歴に入れない**。
- native: `DocRun` は `Finish::Length` の訳も次の履歴に渡している。この差は、後続のプロンプトを変える。
  共通化の段階では、`DocOptions` に「上限に達した訳を履歴に入れるか」の設定を足して、
  それぞれの今の挙動のままにする (native は入れる、Web は入れない)。
- 確かめること: 同じ入力で、各セグメントのプロンプトのトークン列が、今の Web と一致する。

**訳を変える変更 (段階 4)。** 1 つずつ入れて、文書の所要時間と訳の一貫性で評価する。

- 長い段落の文への分割を、native の `DocJob` にも入れる。
- 履歴の上限を、文字数からトークン数にする。
- Web のチェーンの数を増やす (並列)。
- 「上限に達した訳を履歴に入れるか」を 1 つに決める。

評価は、19 文のセットと `bench doc` の文書で、訳が変わった件数と、所要時間を見る
(同じ入力で変わる訳は、履歴の違いから後続に広がるので、件数を見る)。

### 6. Web: 薄いグルー

**段階 1〜4 では、`Translator` が一文書を最後まで駆動する** (`translate` が `run_document_async` を await する)。
次は、段階 5 (常駐 `Scheduler`) での形である。

`yaxus-web` に残すのは次だけ。

- GGUF のストリーミング読み込みと WebGPU の初期化 (今のまま)。
- `Rc<RefCell<..>>` を持たず、**投入と駆動を分ける**。`load_model` が `Runtime` を返し、
  そのコンストラクタが `Scheduler::run` を `spawn_local` で 1 回だけ起動する。
  JS からの `translate(request, on_event) -> Promise` は、job を `JobSource` に積み、完了で解決する
  Promise を返すだけ。wasm-bindgen の `&mut self` を await 中に再入する問題は、これで起きない
  (`&self` で積むだけだから)。
- `cancel(id)`。ページの中止ボタンと、将来のタブの切り替えで使う。
- `Poisoned` で `broken` にし、Worker を作り直す (今のまま)。E2E の GPU 障害のケースがそのまま使える。
- ページは、サーバーの Web UI と同じく、段落が並行して埋まる表示にする
  (イベントの `segment` で場所が決まる)。サーバーの UI と共通の部分は、トランスポート
  (SSE か、Worker のメッセージか) だけを差し替える形にできる。まとめるのは後でよい。
- Web の設定: `max_streams` は KV の容量から決める。KV のアリーナは、チェーンの数 × 1 セグメントの
  コンテキストに合わせて、`MAX_CONTEXT` の固定 (4,096) をやめる。0.8B は 1 ページ 2.1 MB なので、
  128 ページ (16k トークン) で約 270 MB。デバイスの `max_buffer_size` と空きを見て決める。
  応答キャッシュは、E2E の GPU 障害のケースが GPU を通る必要があるので、いまは切る。

### 7. 後回しにするもの

- **下書きモデルの Web 対応**: Engine は対応済みだが、2 つのモデルを 1 つのデバイスに載せるメモリと、
  k 回の連続した読み戻しの往復が割に合うかを測ってから。
- **デコードの往復を隠す**: 次のトークンを GPU 上で次のパスへ渡し、読み戻しを待たずに次のパスを投入する
  (ネイティブの投機でやっている GPU 上のトークン受け渡しの応用)。ストリーム 1 本のときの速度に効くが、
  複数のチェーンが走るときは並行で隠れる。まず 1 トークンあたりの時間のうち、往復の待ちが
  どれだけかを `YAXUS_PROFILE` で測る。
- **ループ検出と回復**、**sliding window の KV の解放**、**OPFS へのモデルのキャッシュ**、
  **2B/8B の Web 対応**、**デバイスの自動選択**、**量子化ごとの品質表示**。
  plamo-translate-desktop との比較で挙がった項目で、この設計の上に独立に足せる。
  ループ検出は `Session` に置く (全フロントエンドに効く)。

## 実施順

当面の目的は **Web の文書翻訳の高速化** である。それには、常駐 `Scheduler` も `JobSource` も、
独立した文書の同時実行も要らない。今の `Translator` が一文書を最後まで駆動する形のまま、
共有の実行ループ (`run_document_async`) に載せ、同じ文書のチェーンから複数のセグメントを Engine に
投入すれば、バッチになる。翻訳全体を覆う現行の GPU エラースコープも、そのまま使える。
常駐 `Scheduler` は、独立した翻訳を並行して走らせる要件が出たときに導入する。

各段階で、ネイティブの出力が変わらないこと (19 文のセットが 19/19 一致)、速度が
ばらつきの範囲に収まること (交互に複数回)、既存のテストと Chrome E2E が通ることを確かめる。
共通化の段階では訳を変えない。訳を変える変更は、段階 4 で 1 つずつ入れる。

1. **一文書を共有の実行ループに載せる (訳は変えない)。**
   - `Generator` を非同期にし (`Send` は外す)、`Session`、`DocRun` / `run_document` を async にする
     (`run_document_async`)。runtime の wasm で動く部分と、ネイティブだけの部分 (`load`) を分ける。
   - Web の `Translator` を、`run_document_async` で一文書を駆動する形に替える。分割、履歴、チェーンの方針は
     今の Web のまま (チェーン 1 本、`split_for_context` のセグメント、上限に達した訳は履歴に入れない)。
   - 確かめること: 各セグメントのプロンプトと出力のトークン列が、現行の Web と一致する。
2. **KV の予約と、文書内のバッチ。** 予約の規則 (4,096 トークンの要求が 32 ページに収まる式) で
   `waiting` に残し、Web のチェーンの数を 1 より大きくしてバッチを有効にする。この段階は訳を変える
   (チェーンを分けると履歴が変わる) ので、段階 4 の評価の対象でもある。`NullBackend` の単体テストで、
   ページ不足でも待つこと、単独で収まらない要求だけがエラーになること、1 つの要求が総ページ数を超えるとき
   その場でエラーになることを確かめる。同じ decode パスで複数のセグメントが進むことを、Chrome E2E で確かめる。
3. **キャンセル。** `Engine::cancel` (待機中の要求と実行中のストリーム)、文書のキャンセル
   (その文書に属する待機中と実行中のセグメントを両方取り消す)。Web の中止ボタンが使う。
4. **訳を変える変更。** 5 の節のとおり、1 つずつ入れて評価する (文分割、トークン単位の履歴、チェーン数、
   上限に達した訳の扱い)。
5. **常駐 `Scheduler` (独立した翻訳の並行実行が必要になったら)。** server の worker から取り出した
   `Scheduler` と `JobSource`、4a のステップ単位のエラースコープ (`begin` より前から開く)、
   `Poisoned`、`Cancel` を受付の上限に関係なく処理すること。確かめること:
   1. 2 件の別々の文書を同時に投入すると、同じ decode パスで両方が進み、それぞれの出力は単独のときと一致する。
   2. GPU 障害 (デバイスロスト、検証エラー、遅れて届くエラー、割り当て失敗) の後に、再読み込みで復帰でき、
      障害のあったステップの `Done` が出ない。
   3. 容量待ちの要求と、実行中の要求のキャンセル。
6. 後回しの項目を、測ってから個別に。

## 実装の状況

- 出発点の `Engine::step_async` と Web の prefix 再利用は main に入っている。
- **段階 1 は実装済み** (ブランチ `async-engine`、訳は変えていない)。
  - `Generator` の非同期化、`Session::step_async`、`run_document_async`、`run_request_async`、
    runtime の wasm ビルド。`Engine` は WebGPU を含む `AsyncReadback` の全バックエンドで `Generator` になる
    (`score` はバックエンドが待てるときだけ)。
  - Web の `Translator` は、一文書を `run_document_async` で最後まで駆動する (チェーン 1 本)。
    分割 (`split_for_context`) だけが Web に残り、履歴、プロンプト、エンジンの駆動は runtime のもの。
    今の Web の履歴の扱いは `DocOptions` の `HistoryRules` (訳の trim、上限に達した訳の除外) で表し、
    native の既定は変えていない。
  - 確かめたこと: Chrome E2E (0.8B Q4_K_M) の全件、12 段落の文書の出力が変更前とバイト単位で同じ
    (プロンプトは 2888 トークン、再利用は 2651 トークンで同じ)、ネイティブの 19 文のセットが 19/19 一致で
    速度はばらつきの範囲 (61.7〜62.0 tok/s)。
- **段階 2 の前半 (KV の予約と待機) は実装済み。** `Engine::admit` は、要求が使いうるページ数
  `ceil(min(prompt + max_new, max_pos) / PAGE)` (`+1` なし) が他の要求の予約と合わせて収まるときだけ要求を
  始め、収まらないあいだは `waiting` の先頭に残す。単独でも収まらない要求 (モデルの位置数を超える、アリーナの
  総ページ数を超える) は、その場で `Event::Error` にする。`NullBackend` の単体テスト 5 件と、GPU のエンジン
  テスト 13 件 (2B) が通った。
- レビューを受けた修正 (済み):
  - 文書の履歴は、チェーンごとに検証済みのペアを持ち、セグメントの完了時に 1 度だけ検証して追加する
    (`DocJob::ready` が毎回、それ以前の全ペアを複製して検証するのをやめた。選ばれた範囲だけを複製する)。
  - Web の統計 (prefill、decode の時間) は、`Session` が測った値を `SegmentEnd` で受け取る。
  - 同期の `step` と `generate` は、`Generator` から外して `SyncGenerator` (`SyncReadback` の `Engine` だけが実装)
    に移した。WebGPU の `Engine` は `Generator` だけで、同期の入口を持たない (誤って呼ぶと、KV を更新したあと
    読み戻しで panic する、という事故を型で防ぐ)。`run_document`、`run_request`、`load_generator` はこちらを使い、
    非同期版 (`run_document_async` など) は `Generator` を取る。
- 段階 5 の `Scheduler` の取り出し (server の worker を runtime の `scheduler` に移した) も実装し、
  ネイティブで検証した。上の順序より先に進んだ部分で、Web はまだ使わない (server だけが使う)。
- **Web の出力はセグメントごとに分けた (済み)。** `on_plan` (各セグメントの前に置く区切り) と
  `on_text(segment, text)` で、ページ (`web/local/layout.js`) が、セグメントごとの本文から出力を組み立てる。
  順序が前後して届いても正しく並ぶ (E2E に検査を足した)。
- **Web でチェーン数を変えられるようにした (既定は 1)。** `?chains=N` (1〜4)。エンジンは最大 4 セグメント
  (`max_streams`、`decode_rows`)、KV のアリーナは 4 セグメントの文脈 (16,384 トークン、`max_pos` は 4,096 のまま)。
  チェーン 1 のとき、E2E は全件通り、12 段落の文書の出力は変わらない。
- **測定 (Chrome、0.8B Q4_K_M、Radeon 780M、9 段落・約 4,000 文字の英文、冷えた状態の 1 回目):**

  | チェーン | 所要時間 | 出力 tok/s (全体) | 1 チェーンと同じ段落 | 1 チェーンとの類似度 (平均) |
  |---|---|---|---|---|
  | 1 | 11.4 s | 74 | - | - |
  | 2 | 8.2 s (1.4 倍) | 103 | 7/9 | 0.97 |
  | 3 | 6.1 s (1.9 倍) | 137 | 3/9 | 0.83 |
  | 4 | 5.4 s (2.1 倍) | 157 | 4/9 | 0.86 |

  同じ入力の 2 回目は、前回の KV がそのまま再利用されて速くなる (チェーンによらず、結果は 1 回目と同じ訳)。
  違いは言い換えの水準で (例: 「ほどなくして…下りていった」と「次の瞬間…消えていき」)、誤訳には見えないが、
  訳の質の優劣は評価していない。段落ごとの `prefill` と `decode` の時間は合計なので、複数のチェーンでは
  経過時間より長くなる。ページは、複数セグメントの文書では経過時間と全体の tok/s を出す。
- **チェーンを分けると訳が変わる理由。** 各段落のプロンプトには、同じチェーンの前の段落の「原文と訳」が履歴として入る。
  チェーンの先頭の段落は履歴が空になる (9 段落をチェーン 2 に分けると、[0-4] と [5-8] で、段落 6 が履歴なしで始まる)。
  実測でも、1 チェーンと違う段落は、チェーンの先頭から始まり、その訳を履歴にする直後の段落へ広がる。
- **隣の段落の原文を文脈として渡す案 (`?neighbor=1`、`neighbor_context`) は、効果がなかった。**
  訳の履歴は渡せないので整合は取れず、全段落のプロンプトが変わる: 近傍ありのチェーン 1 は、近傍なしのチェーン 1 と
  9 段落中 1 段落しか同じでない。近傍ありのチェーン 1 との一致は、チェーン 2、3、4 で 5、3、3 段落 (近傍なしでは 7、3、4)、
  類似度は 0.94、0.94、0.90 (近傍なしでは 0.97、0.83、0.86)。文脈が段落ごとに違うので、履歴の prefix も共有できず、
  再利用は 1,567 から 71 トークンに落ちて遅くなる (チェーン 1 で 11.4 秒から 14.0 秒、チェーン 4 で 5.4 秒から 7.6 秒)。
  訳も、「カーテシー」が全チェーンで「軽く咳払いをしようとした」になるなど、近傍なしより悪い箇所が出た。既定にはしない。
- **ページで切り替えられる (`#chains`)。** 「順に訳す」(1)、2 本、3 本、4 本、「自動」(4 段落に 1 本、最大 4。
  サーバーの UI と同じ規則で、サーバーは最大 8)。選んだ値は localStorage に残す。**既定は「自動」で、サーバーの UI に合わせた。**
  サーバーの UI は、チェーン数を指定せずに文書 API へ段落を送るので、自動の規則 (9 段落で 3 本) で訳している。
  ローカル Web は、もともと 1 つずつ順に訳していて、並列はなかった。
- **Web のチェーンの既定は「自動」 (サーバーの UI に合わせた)。** 速さは 2 倍近い (9 段落で 3 本)。
  訳が変わる点は、サーバーの UI と同じ設計上の性質で、0.8B のローカル Web では、3 本以上で崩れる段落が出た
  (上の測定)。崩れが気になるときは、ページの「並列」を 2 本か「順に訳す」に替えられる。
  別の文書 (長いもの、日本語から英語) での確認は、まだしていない。

- **キャンセルを実装した (段階 3)。**
  - `Engine::cancel(id)`: 待機中の要求は始めずに、実行中の要求はもう 1 パスも与えずに、次のステップで
    `Done { Cancelled }` で終える (KV は prefix の再利用のために残す)。`NullBackend` の単体テストで、待機中、
    実行中、2 度目と未知の要求を確かめた。
  - `Session::cancel_where`。文書は、止まったとき (sink が `false`、セグメントの失敗、外からの取り消し) に、
    待機中と実行中のセグメントを、次の text を待たずにエンジンで取り消す (`run_document_until`)。
  - server の `scheduler` は、クライアントが去った要求と、止まった文書の要求を、待機中のものも含めて取り消す。
  - Web のページに「中止」ボタンを足した。worker は取り消しのメッセージを、実行中の翻訳の後ろに並べず、
    翻訳がステップの合間に確かめる。Chrome E2E で、36 段落の翻訳が、クリックの 71 ms 後に終わり、
    そのあともモデルが使えることを確かめた。
- **server の HTTP 経路を、実モデル (2B + 0.8B の下書き、Radeon 780M) で確かめた。** 変更前のビルドと今のビルドで、
  同じ手順を踏んで出力を比べた: 単一の翻訳、9 段落の文書、文書と別の依頼の同時実行、36 段落の文書の全文は、
  どれもバイト単位で同じ。1 秒でクライアントが切れても (35 秒かかる文書)、直後の短い依頼は 0.17 秒で返り
  (変更前も同じ)、`/healthz` は ok のまま。36 段落の所要時間は 35.52 秒 (変更前) と 35.58 秒 (今)。
- 未実装: ステップ単位の GPU エラースコープと `Poisoned` (段階 5)、訳を変える変更の残り (段階 4)。

## 決めきれていない点

- `Generator` を dyn のままにするか、`enum AnyEngine` にするか。後者はステップごとの boxing を避けるが、
  バックエンドを増やすたびに分岐が増える。ステップが ms 単位なので、いまは dyn のままでよいと考える。
- KV の予約 (prefix を差し引かず、最悪の出力長で予約する) が、実際にどれだけ待たせるか。
  Web の 0.8B で、チェーン 4 本が同時に走るときを、段階 2 の測定で見て、差し引く式や preemption が要るか決める。
- 完了しないチャンクの `end_pass` が、prefill の速度にどれだけ影響するか (見積もりでは小さい)。段階 5 で測る。
- server の UI と Web のページを 1 つの UI にまとめるか (トランスポートだけの差し替え)。
  この設計の範囲外だが、イベントを `yaxus-api` に揃えたことで可能になる。
